# 提速协议（让 Agent 跑满速度）

目标：**在不变更门禁与证据标准的前提下，把墙钟时间压到最短。** 提速不是减少检查，而是消除串行等待、重复阅读和无意义的往返。

四条原则：

1. **并行的对象是「独立工作」**，不是「同一文件的写」。
2. **能一次确认的，不要分两次**；能脚本化的，不要让主会话现场推理。
3. **写操作串行化，读操作并行化**；冲突成本远高于多等一会儿。
4. **独立性优先于速度**：Review 不采信 Dev，Meta 不采信 Review；再快也不能合并这两个角色。

## 1. 提速杠杆总表

| 杠杆 | 做法 | 省什么 | 风险控制 |
|---|---|---|---|
| 并行任务 | 同 CR 内文件不相交的 T 同时派多个 Dev | G2 墙钟时间 | 文件重叠检查 + `max_parallel` |
| 并行评审 | 每个 T 独立 Review，主会话汇总 | G3 墙钟时间 | 每个 Review 仍独立读 diff |
| G2.5 与 G3 并行 | Steward 合大脑不阻塞 Review | 一个完整阶段 | G2.5 必须在 commit 前完成 |
| 门禁合流 | G0+G1 一次确认；S 通道；G3.5/G4 按风险豁免 | 往返轮次 | 合流条件写进 STATUS |
| 预热 | G1 确认前允许 Dev 只读调研（A0） | G1 后的空等 | 写操作仍等 G1 |
| 状态脚本 | `workflow-status.sh` 打印当前门禁与下一步 | 主会话推理 | 只读诊断，不改状态 |
| 上下文复用 | 同 CR 复用 Dev/Steward 会话；报告只回摘要 | token 与重读 | 细节落盘 `reports/` |
| 模型分层 | 机械/记账用快模型，评审/总审用强模型 | 等待时间 | 派单简报写明【模型】 |
| 权限减阻 | 项目 `.claude/settings.local.json` 窄 allowlist | 权限弹窗 | 不放 `Bash(*)`、不放 push/deploy |

## 2. 并行派发

### 2.1 条件（全部满足才并行）

- 任务属于**同一个 CR / 同一份 G1 确认**；
- 任务的 `allowed_paths` **文件不相交**（含测试、文档）；
- 任务之间**没有依赖**（T-002 不需要 T-001 的产物）；
- 每个 T 的 AC 可独立判定；
- 主会话能在合流时判定「谁改了什么」。

任一不满足 → 串行，不要硬并行。

### 2.2 步骤

1. 主会话读 `04-tasks.md`，按「文件 / 模块」把 T 分组，画出并行组。
2. 对每组确认文件不相交；把结果写进 `STATUS.md`：
   ```markdown
   - 并行组：PG-1 = T-001 / T-003 / T-005（文件不相交）；PG-2 = T-002（依赖 T-001）
   ```
3. 一次派发多个子代理（Claude Code 的 Agent 工具可并行调用），每个子代理只带自己的 T、大脑、相关文档。
4. 每个 Dev 写独立报告：`reports/dev-<日期>-<T>.md`；不要合并成一份。
5. 全部返回后，主会话做**合流检查**：`git status` / `git diff --stat` 确认没有同一文件被两个 T 改过。
6. 并行组内全部 G2 完成后，再统一进入 G2.5 / G3。

### 2.3 并行度上限

- 默认同时最多 **3 个写代理**（`max_parallel: 3`）。
- 超过时改分批；批次之间先合流、再开下一批。
- 同一文件被两个 T 触及 → **立即串行化**，并在报告里说明拆分原因。
- 只有 Steward 能写 `PROJECT_BRAIN.md`；并行 Dev 只提交「上下文增量」，不得同时改大脑。

### 2.4 并行派单模板

在 `SKILL.md` §3 的简报基础上增加两行：

```text
【并行组】PG-1（T-001 / T-003 / T-005；文件不相交，单独报告）
【模型】实现=主模型 / 评审=强模型 / 记账=快模型
```

## 3. 门禁合流

不是所有改动都值得跑满 G0–G4。合流必须写进 `STATUS.md`，并由用户确认。

| 场景 | 合流方式 | 保留什么 |
|---|---|---|
| 需求清楚、单 CR | **G0 + G1 一次确认**：CR 卡、R/AC/T、信封一起给用户 | 编号、AC、信封、`check-docs --gate g1` |
| S 小改（≤3 文件、无接口/数据/鉴权/依赖/构建） | S 快车道：G1-lite → Dev → Review 快评 → commit → 用户验收 | AC、证据、A1c、主会话 commit |
| 小 diff、单模块 | **G2.5 并入 G3**：Steward 在 Review 前合并，不单独设门 | WORKLOG 记 `gate=G2.5` 一行 |
| 单模块、低耦合 | **G3.5 豁免**：STATUS 写 `G3.5 豁免：<理由>` | Review 报告 + G3 接受 |
| 纯文案/样式/文档 | **G4 豁免**：按 `SKILL.md` §2.2 规则 | G3 报告 + 提交 |

**不允许合流**：跨模块、数据模型/迁移、鉴权/权限、新增依赖、发布风险高的改动；这些必须按完整门禁走。

## 4. 预热与预读

- G1 确认前，Doc 可以派 Dev 做**只读调研**（A0）：定位改动面、调用方、测试、风险；产出调研笔记，不写代码。
- 调研结论可直接喂给 G1 影响预判，减少 G1 后的第一轮阅读。
- 预热不改变门禁：**写操作仍然等 G1 确认 + 信封**。

## 5. 状态脚本与交接

```bash
# 打印当前门禁、下一步、必跑检查；只读，不改任何文件
$LOSSKILL_HOME/scripts/workflow-status.sh <文档根目录> [--project-root <项目根>]
```

输出包括：

- 当前 CR / 门禁 / 通道 / 并行组；
- 信封状态（policy、到期、提交额度）与 G3 接受状态；
- 最近 5 条 WORKLOG；
- **下一步**：该派谁、先跑哪条 `check-docs`、缺什么材料；
- 门禁检查的退出码（若加 `--check`）。

主会话每次接手先跑一次，不要凭记忆推断当前阶段。

## 6. 模型分层

派单时在简报里写明【模型】，按任务性质选择：

| 任务 | 建议 |
|---|---|
| 文档整理、报告记账、日志回填 | 快模型 |
| 功能实现、重构、调试 | 主模型（默认） |
| 独立评审、总审、UAT | 强模型（不要用快模型替代） |
| 只读调研、找文件 | 快模型 / 搜索代理 |

原则：**判断类任务不降级**；机械类任务不占用强模型。

## 7. 上下文与 token

- 每个子代理只读：`PROJECT_BRAIN.md` → 自己的 T/AC → 改动面 + 调用方 + 测试；不通读全仓库。
- 报告只回摘要 + 报告路径；大段证据落盘 `reports/`。
- 同一 CR 内复用 Dev / Steward 会话；Review 每个 CR 新建，返工可复用。
- 并行组内的子代理不要互相转述；主会话只保留合流结论。

## 8. 度量（写进 STATUS 或报告）

| 指标 | 怎么记 |
|---|---|
| 并行任务数 / 墙钟时间 | G1 到 G3 的实际耗时、并行组数 |
| 合并冲突 | 同一文件被多个 T 触及的次数 |
| 重复阅读 | 同一文件被多个角色重复读的次数（抽查） |
| 门禁往返 | 每个门禁的轮次（G3 通过 / 返工） |
| 漏检 | G4 发现 Review 漏掉的 P0/P1 数 |

没有度量就无法判断「更快」是否成立。

## 9. 反模式

- ❌ 为并行而并行：文件重叠还硬派两个 Dev，合流时冲突。
- ❌ 多个 Agent 同时改 `PROJECT_BRAIN.md`。
- ❌ 用并行跳过 G3 或让 Review 互相背书。
- ❌ 为了快把判断类任务降级到快模型。
- ❌ 合流不记录：STATUS 看不出走了哪条通道、合了哪些门。
- ❌ 用「节省 token」当跳过高风险门禁的理由。

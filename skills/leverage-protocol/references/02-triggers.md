# 触发器表：用户不点名，但该主动想到的能力

## 规则

1. 只在**会改变做法**时提；不相关不提。
2. 最多 3 项，每项 1 行；用"要不要我…"，不用"你应该…"。
3. 低风险且明显有益 → 直接做，末尾一行说明。
4. 会改变范围/成本/架构 → 一句话问。
5. 用户说不用 → 立即停止。

机器匹配：`scripts/capability_index.py plan "<任务>"`（数据源 `domains.json`）。
本文件是给人看的触发器表；两者信号应保持一致。

---

## 一、任务信号 → 能力域

| 用户信号 | 能力域 | 该主动做什么 |
|---|---|---|
| 加功能 / 改一下 / 实现 X | 架构、测试、错误处理、兼容性 | 先定边界与验收；补边界测试 |
| 重构 / 拆分 / 模块化 / 微服务 | 架构与边界 | 先给 2–3 方案与回滚 |
| 用个设计模式 / 工厂 / 策略 / 状态机 | 设计模式与惯用法 | 先确认是否过度设计；给"不用模式"选项 |
| 写接口 / API / SDK | API 与契约 | 先定输入/输出/错误/兼容 |
| 存数据 / 表结构 / 迁移 / 索引 | 数据模型与迁移 | 先确认约束、迁移回滚、锁表风险 |
| 性能 / 慢 / 优化 / 数据量变大 | 性能与资源 | 先测量再优化；给基准方法 |
| 并发 / 线程 / 锁 / async | 并发与异步 | 画共享状态与同步协议；查竞态/取消 |
| 外部调用 / 网络 / 重试 / 超时 | 错误处理与韧性 | 补失败分类、退避、幂等 |
| 上线 / 发布 / 灰度 / 回滚 | 发布与回滚 | 给回滚路径与兼容性 |
| 认证 / 权限 / 密钥 / 用户输入 | 安全与隐私 | 检查输入、权限、敏感信息 |
| 日志 / 监控 / 排障 | 可观测性 | 补关键日志/指标/上下文 |
| 写文档 / 设计说明 / ADR | 文档与决策记录 | 记录取舍与使用方式 |
| 测试 / 覆盖率 / 回归 | 测试策略 | 正常+边界+失败路径；确认断言会失败 |
| 不确定怎么做 / 方案对比 | 架构、设计模式 | 先给候选与取舍，不直接动手 |

## 二、按任务级别的默认触发器

### S（小改）

- 只主动提**一个**：与改动直接相关的验证或边界。
- 例："这个改动没碰错误路径，要不要我顺手补一个失败用例？"

### M（功能）

- 默认检查：契约、边界、失败路径、兼容性。
- 最多提 2 项，优先"会影响验收"的。

### L（跨模块/数据/权限/发布）

- 必须先提：方案与取舍、回滚、分步验证。
- 未确认前不进入大规模实现。

---

## 三、不该主动提的情况

- 用户明确"最小改动 / 先跑通 / 只要草稿"。
- 任务与能力域无关（纯算法题、翻译、名词解释）。
- 提了会显著扩大范围，而用户当前只想验证一个点。
- 同一项已提过且用户拒绝。
- 你并没有足够上下文判断它是否适用（先问，而不是先建议）。

---

## 四、"会改变做法"的判断

问自己三个问题：

1. 如果采用它，代码/方案会不会不同？会 → 值得提。
2. 采用它的成本是否超过当前任务的收益？是 → 只提一句，不展开。
3. 不提它，交付会不会有已知缺陷？会 → 必须提。

三个都否 → 不提。

---

## 五、与具体 Skill 的关系

- 匹配到已装 Skill → 交给它执行；本表只负责"想起来"。
- 没有匹配 Skill → 用通用知识 + 本表检查点；在输出中说明"没有套用现成技能"。
- 不要为了用 Skill 而用 Skill；也不要用本表替代领域 Skill 的详细流程。

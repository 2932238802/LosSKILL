# 项目适配：L2 怎么写

## 目标

L0 是通用的 12 行；L2 只放**这个项目真实存在**的东西：

- 验证命令（可复制、可执行）
- 项目专属信号（用户会怎么说）
- 本地雷区（踩过一次的坑）

通用建议在网上都有；L2 的价值是"这个仓库的真相"。

---

## 步骤

### 1. 检测栈

```bash
python3 scripts/capability_index.py profile --cwd <项目>
```

会识别 Cargo / package.json / pyproject / go.mod / 测试目录 / CI / Docker，并写
`<项目>/.claude/capability-profile.json`（需用户同意写文件）。

### 2. 找真实验证命令

优先级：
1. CI 配置（`.github/workflows/*.yml`）里的 `run:`；
2. `README` 的"开发/测试"段；
3. `Makefile` / `justfile` / `scripts/`；
4. 都找不到 → 问用户，不要猜。

每条命令必须实际跑过一次（或用户确认），并记日期。

### 3. 写 L2 文件

路径：`references/projects/<项目>.md`。模板见下。

### 4. 接 L0

在项目根：

- `AGENTS.md` 顶部放 `00-agents-snippet.md` 的标准片段；
- `CLAUDE.md` 放一行 `@AGENTS.md`（Claude Code）；
- 已有文件则合并，不覆盖。

### 5. 验收

新开会话，问一个非平凡任务，确认：
- 会分级；
- 交付时回答三问；
- 能引用 L2 的命令。

---

## L2 模板

```markdown
# <项目名> 项目适配

- 最后验证：YYYY-MM-DD
- 栈：<语言/框架/数据库/部署>
- 入口：<主目录/服务>

## 验证命令（按改动类型）

| 改动 | 命令 | 最后验证 |
|---|---|---|
| 后端 | `<命令>` | YYYY-MM-DD |
| 前端 | `<命令>` | YYYY-MM-DD |
| 全量 | `<命令>` | YYYY-MM-DD |

## 项目专属信号

| 用户会说 | 实际涉及 |
|---|---|
| ... | ... |

## 雷区

- <坑 + 正确做法>

## 不要做

- <本项目的禁区>
```

---

## 维护规则

- **命令必须带最后验证日期**；超过 90 天标"可能过期"，下次用到先验证。
- 命令改名/删除时，同步更新 L2；否则比没有更危险。
- 不写密钥、令牌、内网地址、个人隐私。
- 一个项目一个文件；不要把多项目混在一起。
- L2 只写"项目特有"，与 L1 重复的内容删掉。

---

## 多项目推广顺序

1. 先做一个（如 Theseus），跑通 L0 + L2 + 一次真实交付。
2. 记录实际效果：分级是否被遵守、三问是否被回答、验证是否真的跑了。
3. 再复制到下一个项目（Vesta、LosNote…），只换 L2 内容。
4. 每个项目单独验收，不假设"一套就通用"。

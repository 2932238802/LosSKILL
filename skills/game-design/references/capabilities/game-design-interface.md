# 能力：游戏界面与反馈设计

## R — 原文

> "从最简单的层面上来说，界面就是存在于玩家和游戏世界之间的所有事物。"（第 15 章，PDF p308–310）

> "如果你的界面不会在十分之一秒内对玩家的输入做出反应，玩家就会开始觉得你的界面出了问题。"（第 15 章，PDF p316）

> "如果它看上去不同，它的行为也应该不同。"（第 15 章，PDF p329–330）

## I — 自述

界面不是 UI 皮肤，而是玩家与游戏世界之间的全部通道：物理输入设备、虚拟界面层、物理输出。设计界面等于设计六条数据流：

1. 物理输入 → 游戏世界
2. 游戏世界 → 物理输出
3. 物理输入 → 虚拟界面
4. 虚拟界面 → 游戏世界
5. 游戏世界 → 虚拟界面
6. 虚拟界面 → 物理输出

每条箭头都要写明映射规则（速度、加速度、延迟、显示位置、字体、颜色）。六条互相配合，界面规格才算完整。

信息展示则按四步：列出全部信息 → 按"每一刻必须知道 / 时不时瞥一眼 / 需要时再查"分级 → 列出可用信息通道（屏幕位置、头像、音效、敌人身体、对话气泡）→ 把信息映射到通道并画草图。

两条硬规则：输入反馈必须在 0.1 秒内出现；外观差异必须对应行为差异，反过来外观相同的行为必须相同。

## A1 — 应用示例

书中案例：作者用"六箭头"分析一款格斗游戏（第 15 章）——发现"世界→虚拟界面"这条箭头缺失：玩家看不到自己的硬直状态，导致误判；补一个极简的状态提示后，操作感明显改善。原书未给量化测试。

书中案例：某个按键在不同界面里有时"确认"、有时"关闭"（第 15 章）——外观相同但行为不同，玩家反复误触；改为行为一致后误操作下降。作者称这是"外观—行为一致性"的典型违反。

## A2 — 何时触发

- 用户说"操作手感很怪""玩家找不到信息""UI 怎么排""按键延迟""新手教程怎么做"。
- 用户在设计 HUD、菜单、交互规格、信息层级。
- 用户要把设计文档里的界面部分写成可实现规格。
- 英文信号：game UI、HUD、input latency、affordance、usability、feedback loop。

与相邻能力的区别：`game-design-experience` 管体验与节奏；本能力管**玩家与系统之间的通道**；`game-design-playtest` 验证玩家是否真的看懂。

## E — 执行

**输入契约**：游戏世界规则与状态清单；输入设备；目标平台与分辨率；玩家需要知道的信息清单。

**步骤**

1. **画六箭头**：逐条写出映射规则；标出缺失或冲突的箭头。完成标准：六条都能用"输入 → 规则 → 输出"说清。
2. **信息分级**：列全部信息，分三级（每刻必知 / 偶尔瞥 / 按需查）。完成标准：每条信息有级别，而不是全部堆在 HUD。
3. **分配通道**：为每条信息选通道与编码维度（数字、颜色、大小、形状、位置、声音）；同一维度不要同时承载两种含义。完成标准：任一信息能回答"何时需要、从哪看到、用什么编码"。
4. **压延迟**：测量按键到反馈的时间；把确认反馈压到 0.1 秒内；重动作先给即时确认，再播完整动画。完成标准：玩家不会因"按了没反应"而重复按键。
5. **一致性检查**：列出所有视觉差异，问"玩家会预期什么功能差异"；要么让行为真的不同，要么取消差异；反向检查相同外观是否行为一致。
6. **画草图试排**：大量低保真草图，快速比较信息密度与视线路径；用纸板原型测试（见 `game-design-playtest`）。

**输出契约**：六箭头映射表；信息—级别—通道—维度表；延迟预算表；外观—行为一致性检查表；界面草图。

**判停**：信息无法分级（全部"必须知道"）→ 先砍系统，不是压缩字号；映射规则写不出 → 交互规格未完成，不要进入美术。

## B — 边界

- 虚拟界面层可薄可厚；桌游可能几乎没有虚拟层，不能照搬电子游戏方案。
- 0.1 秒是感知阈值，不是所有动作都要 0.1 秒完成；重动作可以有更长恢复，但必须有即时确认。
- 纯装饰差异若足够微弱可以保留，但不能让玩家产生功能预期。
- 原书未讨论文化差异对颜色/形状预期的影响；跨文化产品需额外验证。
- 不是视觉设计/美术风格能力；本能力只管通道、信息与一致性。

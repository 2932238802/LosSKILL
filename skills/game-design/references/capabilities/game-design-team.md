# 能力：团队协作与设计文档

## R — 原文

> "一个更容易成功的方法是尽可能多地让团队成员参与到设计过程中去。"（第 25 章，PDF p476–478）

> "游戏文档有且只有两个目的：备忘与沟通。"（第 26 章，PDF p485–486）

> "游戏中的重要组成部分都应该能被海报上的示意图解释清楚。"（第 26 章，PDF p487, p491）

## I — 自述

设计能否被正确实现，取决于团队是否共享同一套决策与上下文。

**共同设计**的流程是：扩大参与（头脑风暴阶段人越多越好）→ 核心设计团队独立设计 → 设计讨论会达成共识 → 设计报告会向全团队汇报并接受批评（常变成下一轮头脑风暴）→ 细节由有兴趣/有能力的人组成小组推进 → 共识尽快传回全员。前提是设计师放下"必须由我拍板"的自尊，但保留最终取舍责任。

**文档**只有两个目的：备忘（记住数千项设计决定及理由，避免重复解决同一问题）和沟通（让团队、管理层、外包、玩家读到并反馈）。先问"这份文档服务哪个目的、给谁看"，再决定写什么、写多详细。原书列出十五类文档，但明确说没有通用模板，项目应按需增删，小团队可合并。

**一页设计/海报测试**：把游戏的重要组成画成一张海报式示意图，核心系统、循环、受众信息都能在图上解释清楚。画不出来，说明团队没有共同全局观。

## A1 — 应用示例

书中案例：作者在迪士尼/EA 的经历（第 25–26 章）——团队用"设计报告会"让全员批评方案，设计师当场记录而不辩护；报告会结束后，批评意见进入下一轮头脑风暴。作者称这让缺陷更早暴露，但未给项目数据。

书中案例：一页设计（第 26 章，转述 Stone Librande）——用一张图讲清游戏循环、资源流向与玩家动机，管理层据此对齐，而不是读 200 页 GDD。

## A2 — 何时触发

- 用户说"团队对设计有分歧""设计文档怎么写""要不要写 GDD""怎么让程序/美术理解设计""文档没人看"。
- 用户要建立评审流程、决策记录、跨职能协作方式。
- 用户团队小，纠结要不要写文档、写多少。
- 英文信号：game design document、GDD、one-page design、team alignment、design review process。

与相邻能力的区别：`game-design-review` 是方案质量门；本能力是**人与信息的组织方式**；`game-design-prototype` 是开发流程。

## E — 执行

**输入契约**：团队规模与角色；当前决策方式；已有文档清单；项目阶段；远程/线下协作条件。

**步骤**

1. **定参与结构**：明确哪些决定全员参与、哪些由核心小组、哪些由个人拍板；为每类决定写"谁提案、谁评审、谁拍板、何时截止"。
2. **开设计报告会**：设计师陈述 → 全员批评 → 记录不辩护 → 分类（事实错误/方向问题/细节建议）→ 进入下一轮。
3. **文档目的声明**：每份文档写"目的（备忘/沟通）+ 读者 + 更新责任人 + 更新频率"；既不回看也不讨论的文档删掉。
4. **选文档类型**：从设计（概述、细节设计、故事概要）、工程（技术设计、管线、系统限制）、美术（美术圣经、概念纵览）、制作（预算、资源、日程、故事圣经、剧本、教程）、玩家（攻略）中按需裁剪；小团队合并同类项。
5. **画一页设计**：把核心循环、资源流、玩家动机、关键系统画在一张图上；让非设计角色只看图复述游戏怎么玩。完成标准：他们能复述正确。
6. **建立决策记录**：每次评审记录"决定、理由、被否方案、负责人、复审时间"；新成员先读决策记录，而不是从头问。

**输出契约**：参与与决策矩阵；设计报告会记录；文档清单（类型 | 目的 | 读者 | 责任人 | 频率）；一页设计图；决策日志。

**判停**：文档既不被回看也不被讨论 → 删除或改写；一页图画不出核心循环 → 设计本身未收敛，先回去收敛。

## B — 边界

- 没有通用文档模板；照搬大厂 GDD 会压垮小团队。
- 共同设计不等于所有人对所有事投票；过度参与会拖慢决策，作者未给团队规模与会议频率。
- 文档写完即可能过时；本能力不解决版本控制与保密/外包场景。
- 一页设计对复杂游戏可能不够，需要分层；原书未给图的语法标准。
- 书中团队建议默认团队有预算与跨职能成员；一人开发需自行裁剪。

# AI 注释保护规则

## 1. 触发时机

处理任何代码、配置文件、脚本或文本文件时，**先扫描注释**。只要出现下列任一形态，本规则立即生效：

```
// LOS: 2026-11-15: 手动添加的业务逻辑，与支付流程强相关
# LOS: 自定义全局变量，后续要改
/* LOS: 数据库索引：此处必须保留，否则查询性能下降 */
-- LOS: SQL 里的临时口径
<!-- LOS: 文档里的手工批注 -->
```

判定方式：注释符之后（可含空格）紧跟 `LOS:` 或 `los:`。前缀大小写不敏感，**但注释正文必须原样保留，包括大小写、空格与标点**。

## 2. 硬性约束

| # | 规则 |
|---|---|
| 1 | **禁止改写**：`LOS:` 注释的正文一个字符都不能改（包括修错别字、补标点、统一格式）。 |
| 2 | **禁止删除**：哪怕该注释描述的代码被你重写，注释也必须保留在原处。 |
| 3 | **禁止移动**：注释要留在原来的行/块位置；不要在整理格式时把它挪到别的行。 |
| 4 | **禁止覆盖**：生成整段代码、格式化、自动修复、批量替换时，不得让 `LOS:` 注释被新内容吞掉。 |
| 5 | **必须记录**：任务结束时，回复里列出「保留的 LOS: 注释」——文件路径 + 行号 + 原文。 |

## 3. 与其他操作冲突时怎么办

- **格式化工具会重排注释**（如 Prettier / clang-format / black）：先确认格式化不会改动 `LOS:` 注释位置；不确定就跳过这几个文件的格式化，并说明原因。
- **重构需要改动注释所在代码块**：可以改代码，注释保留；如果注释内容因此变得不准确（例如描述的字段已删），**不要擅自改注释**，而是在回复里提示用户：「`<文件>:<行>` 的 LOS 注释可能已过期，请确认是否更新」。
- **整文件重写 / 删除文件**：属于高风险操作，必须先向用户确认，并给出该文件内所有 `LOS:` 注释的清单。
- **生成新文件**：不得凭空写出 `LOS:` 注释（那是用户的手写标记），只允许原样复制已有的。

## 4. 交付格式

每次涉及 `LOS:` 注释的改动，回复末尾附一段：

```
## 保留的 LOS 注释（未被修改）
- src/pay/order.ts:42  // LOS: 2026-11-15: 手动添加的业务逻辑，与支付流程强相关
- scripts/deploy.sh:7  # LOS: 只在周五发布窗口跑
```

如果某个 `LOS:` 注释可能因本次改动失效，单独列一节「待你确认」并说明原因。

## 5. 不用于

- 文件里根本没有注释的纯逻辑改动（此时无需走本规则）。
- 纯写作、翻译、非代码文本。
- 用户明确要求「把我这些 LOS 注释也一起改掉」时——此时按用户当次指令执行，但需逐条确认要改哪些，不批量处理。

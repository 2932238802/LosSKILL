# 上下文协议（四角色通用）

目标：**让新启动的 Agent 不必重读整个项目**，同时不牺牲正确性。
核心做法：共享大脑文件 + 每份报告的增量块 + Steward 合并 + 克制的阅读预算。

## 1. 记忆分层

| 层 | 位置 | 放什么 | 谁维护 |
|---|---|---|---|
| 大脑 | `PROJECT_BRAIN.md`（项目根；没有时找 `<文档根目录>/PROJECT_BRAIN.md`） | 架构地图、模块边界、不变量、契约、验证命令、热点、测试地图、决策索引、最近变更 | Doc 维护稳定事实；Steward 合并增量 |
| 项目文档 | `<文档根目录>/00–05` | 需求、AC、设计、任务、决策的完整内容 | Doc；Dev 更新任务状态 |
| 报告 | `<文档根目录>/reports/` | 每次开发的证据、评审结论、总审结论 | 各角色 |
| 代码与测试 | 仓库 | 事实最终来源 | Dev |

大脑是**索引与约束**，不是代码副本，也不是文档摘要。细节留在文档和代码里，大脑只告诉 Agent「去哪看、什么不能破」。

## 2. 开工第 0 步（所有角色）

1. 读 `PROJECT_BRAIN.md`。不存在时：说明缺失，建议先跑 `scripts/bootstrap-project.sh` 或让 Steward 补建；不要假装自己知道全局。
2. 读与任务相关的模块卡 `brain/modules/<module>.md`（如果有）。
3. 按角色读取任务文档（CR/AC/设计/任务/决策）。
4. 只读**改动面 + 直接调用方 + 相关测试**的代码。
5. 在报告中列出实际读过的文件；解释为什么读它。

## 3. 阅读预算

| 分级 | 代码文件上限 | 超出时 |
|---|---|---|
| S 小改 | 5 | 说明为什么必须多读 |
| M 功能 | 15 | 分阶段：先接口/调用方，再实现/测试 |
| L 重活 | 不限，但分阶段 | 每阶段结束写一次增量与下一步 |

预算不是硬性禁令，是**警报**：超预算时先停下来确认自己是否在通读无关代码。

## 4. 上下文增量（每份报告必须有）

在报告的「下一步交接」之前加：

```markdown
## 上下文增量

- 触及模块：<模块名 / 路径>
- 不变量变化：无 / 新增 / 修改（写清哪条）
- 契约变化：无 / 接口 / 事件 / 数据模型 / 配置（写清）
- 测试变化：新增 / 修改 / 删除（路径）
- 大脑需要更新的节：2 / 3 / 4 / 6 / 7 / 8 / 9（没有写「无」）
- 发现的过期信息：<大脑或文档里与代码不一致的地方；没有写「无」>
```

没有增量块视为报告不完整。Steward 在 G2.5 合并；Dev 不直接大改大脑（只提交增量）。

## 5. 检查点

| 检查点 | 谁 | 做什么 |
|---|---|---|
| G1 确认后 | Doc + Steward | 影响预判：本次会碰哪些模块/不变量/契约；大脑是否需要先更新 |
| G2 完成 | Dev | 写「上下文增量」；列出实际读过的文件 |
| G2.5 | Steward | 合并增量到大脑；更新「最近变更」；标记过期内容 |
| G3 评审 | Review | 读大脑 + 增量 + diff；按测试地图跑回归；写 review-index |
| G3.5（可选） | Steward | 跨模块/跨 CR 的一致性检查；发现隐性耦合 |
| G4 | Steward/Meta | 风险触发的全链路总审；复核大脑与实现是否一致 |

## 6. 会话复用

- **同一 CR 内**：Dev 用同一个会话完成实现与返工；Steward 用同一个会话完成 G1/G2.5/G3.5。
- **Review**：每个 CR 新建会话以保持独立性；同一 CR 的返工可复用会话以保持基线。
- **跨 CR**：一律新建会话，只带大脑 + 相关报告路径，不带上一轮全文。
- 上下文接近上限时：先写增量与交接块，再新开会话；不要带着半截上下文硬撑。

## 7. 大脑维护规则

- 只写稳定事实与导航；不复制代码，不写频繁变化的实现细节。
- 每条关键结论尽量带 `文件:行号`、命令或报告链接。
- 验证命令带「最后验证」日期；超过 90 天标「可能过期」。
- 架构、契约、不变量变化时，Steward 必须在「最近变更」留记录。
- 大脑超过 ~200 行时，把模块细节拆到 `brain/modules/`。
- 大脑与代码冲突时，**以代码 + 实际运行结果为准**，并立即标记大脑过期。

### 7.1 成熟度

大脑头部应写明状态：

```markdown
> 状态：L1 草稿 ｜ 最后验证：2026-11-20 ｜ 维护：Steward
```

| 级别 | 标志 | Agent 行为 |
|---|---|---|
| **L0 缺失** | 没有文件 | 不阻塞只读调研；先说明缺失，建议 Steward 建档；结论多标 `[推断]` |
| **L1 草稿** | 有导航与命令，但命令未实跑 | 正常使用，但代码多读一些；未验证命令标「未验证」 |
| **L2 已验证** | 关键命令至少成功跑过一次 | 正常使用；过期项标「可能过期」 |
| **L3 维护中** | 每个 CR 在 G2.5 合并增量 | 默认目标；漂移检查按 7.3 执行 |

### 7.2 首次填充（Steward，时间盒 45 分钟）

1. 列顶层目录与清单文件（`package.json` / `Cargo.toml` / `pyproject.toml` / `go.mod`），确定入口与运行方式。
2. 找构建/测试配置，填第 5 节命令；能便宜跑一次就跑，跑不了标「未验证」。
3. 用最近 90 天 churn 找热点模块：`git log --since=90.days --name-only --pretty=format:`，填第 2/6 节。
4. 从 README、测试断言、现有 ADR 提炼不变量与契约，填第 3/4 节。
5. 其余节标「待补充」；不要为填满而编造。
6. 写 `状态：L1` 与「最后验证」日期；不要阻塞 G0/G1。

### 7.3 漂移检查（G2.5 / G4）

- 改动文件能否映射到第 2 节的模块？不能 → 更新模块表或标「未归类」。
- 是否改了契约/不变量？是 → 更新第 3/4 节，并在第 9 节留记录。
- 验证命令是否失败或改名？是 → 标「可能过期」，写明新命令或待确认。
- 某个节超过 90 天未复验？→ 标「可能过期」。
- 大脑与代码冲突？→ 代码/运行结果为准，大脑记为「过期」。

## 8. review-index（评审记忆）

`<文档根目录>/reports/review-index.md` 按模块记录：

| 模块 | 历史缺陷类型 | 高发位置 | 建议检查 |
|---|---|---|---|
| ... | 并发/边界/契约/权限… | 文件:行 | 下次评审优先看什么 |

Review 开工时读它，但**不把它当证据**：先独立看 diff 与影响面，形成初步假设后再读 review-index，用它决定「先看哪里」，而不是决定「结论是什么」。每轮评审后追加一行，不写长篇。

### 8.1 工作日志（WORKLOG.md）

`WORKLOG.md`（项目根）是跨角色、跨 CR 的**活动索引**，只追加、最新在最上面：

| 字段 | 内容 |
|---|---|
| ID | `LOG-YYYYMMDD-HHMMSS`，脚本生成 |
| 时间 / 角色 / 门禁 | 谁在什么时候、哪个门禁做了什么 |
| CR / T | 对应需求卡与任务 |
| 做了什么 | 一句话结果，不写“已完成开发” |
| 报告 / Commit / AUTH | 详细证据的指针 |
| 状态 | 完成 / 返工 / 阻塞 / 有条件通过… |

- 优先用 `scripts/finish-report.sh --report <报告路径>`：它解析报告头部的 `report-meta`，同时写 WORKLOG 与 AUTH，并回填 `LOG-ID`。
- 手工补录时才直接用 `scripts/worklog.sh`（在项目根执行，`--file WORKLOG.md`），避免格式漂移；报告写完后立即记一行，并在报告里写 `LOG-ID`。
- **不要**把它当 STATUS（当前状态）或大脑（架构事实）：它是历史索引。
- Steward 在 G4 审计：每个门禁/报告是否都有对应行；缺失记 P1 流程缺陷。
- 更正不删旧行：追加一条“更正”，在「做了什么」里引用原 `LOG-ID`。

没有度量就无法判断「更高效」是否成立。

## 9. Steward 检查点 Prompt（可直接复制）

### G1 影响预判

```text
【项目路径】<绝对路径>
【项目大脑】PROJECT_BRAIN.md
【本次 CR】CR-xxx
【任务】一句话目标
请只做三件事：
1. 本次会触及哪些模块、不变量、契约（引用大脑节号与文件:行）；
2. 大脑中哪些信息缺失或可能过期；
3. 给出 A1/A2/A3 的初步分级与范围信封草案（路径、命令、提交上限、到期）。
不要改代码，不要写实现方案。
```

### G2.5 合并增量

```text
【项目路径】<绝对路径>
【项目大脑】PROJECT_BRAIN.md
【Dev 报告】<路径>
【Diff】<commit 范围>
请：
1. 从报告「上下文增量」与 diff 中提取需要合并的事实；
2. 更新大脑第 2/3/4/6/7/8/9 节（只改有证据的部分）；
3. 列出仍过期或无法确认的项，标明负责人；
4. 输出本次合并摘要，不要复述代码。
```

### G3.5 跨模块检查

```text
【项目路径】<绝对路径>
【项目大脑】PROJECT_BRAIN.md
【本次 CR】CR-xxx
【相关报告】Dev / Review 路径
请检查：
1. 本次改动是否破坏其他模块依赖的契约或不变量；
2. 是否与最近 5 条「最近变更」冲突；
3. 是否有未归类的模块/文件；
4. 给出「继续 / 返工 / 需要用户决策」的结论与证据。
```

## 10. 反模式

- ❌ 每个 Agent 都从 `00-overview` 读到代码，重复付费。
- ❌ 把大脑写成第二份架构文档，没人维护。
- ❌ 大脑过期后仍被当作事实；没有「最后验证」日期。
- ❌ 报告只写「已完成」，不写增量，Steward 无法合并。
- ❌ Review 通读全仓库找问题，而不是按 diff + 影响面 + 测试地图。
- ❌ 为了省 token 跳过关键调用方/测试的阅读。

## 11. 度量

每个 CR 在 `STATUS.md` 或报告里记录：

- 各角色实际读过的文件数 / 是否超出预算
- 重复读同一文件的次数
- G3 发现的 P0/P1 数、Review 漏检数
- 从 G1 到 G3 的耗时与 token（有数据时）

没有度量就无法判断「更高效」是否成立。

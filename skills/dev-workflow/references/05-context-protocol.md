# 上下文协议（四角色通用）

目标：**让新启动的 Agent 不必重读整个项目**，同时不牺牲正确性。
核心做法：共享大脑文件 + 每份报告的增量块 + Steward 合并 + 克制的阅读预算。

## 1. 记忆分层

| 层 | 位置 | 放什么 | 谁维护 |
|---|---|---|---|
| 大脑 | `PROJECT_BRAIN.md`（项目根；没有时找 `<文档根目录>/PROJECT_BRAIN.md`） | 架构地图、模块边界、不变量、契约、验证命令、热点、测试地图、决策索引、最近变更 | Doc 维护稳定事实；Steward 合并增量 |
| 项目文档 | `<文档根目录>/00–05` | 需求、AC、设计、任务、决策的完整内容 | Doc；Dev 更新任务状态 |
| 报告 | `<文档根目录>/reports/` | 每次开发的证据、评审结论、总审结论 | 各角色 |
| 代码与测试 | 仓库 | 事实最终来源 | Dev |

大脑是**索引与约束**，不是代码副本，也不是文档摘要。细节留在文档和代码里，大脑只告诉 Agent「去哪看、什么不能破」。

## 2. 开工第 0 步（所有角色）

1. 读 `PROJECT_BRAIN.md`。不存在时：说明缺失，建议先跑 `scripts/bootstrap-project.sh` 或让 Steward 补建；不要假装自己知道全局。
2. 读与任务相关的模块卡 `brain/modules/<module>.md`（如果有）。
3. 按角色读取任务文档（CR/AC/设计/任务/决策）。
4. 只读**改动面 + 直接调用方 + 相关测试**的代码。
5. 在报告中列出实际读过的文件；解释为什么读它。

## 3. 阅读预算

| 分级 | 代码文件上限 | 超出时 |
|---|---|---|
| S 小改 | 5 | 说明为什么必须多读 |
| M 功能 | 15 | 分阶段：先接口/调用方，再实现/测试 |
| L 重活 | 不限，但分阶段 | 每阶段结束写一次增量与下一步 |

预算不是硬性禁令，是**警报**：超预算时先停下来确认自己是否在通读无关代码。

## 4. 上下文增量（每份报告必须有）

在报告的「下一步交接」之前加：

```markdown
## 上下文增量

- 触及模块：<模块名 / 路径>
- 不变量变化：无 / 新增 / 修改（写清哪条）
- 契约变化：无 / 接口 / 事件 / 数据模型 / 配置（写清）
- 测试变化：新增 / 修改 / 删除（路径）
- 大脑需要更新的节：2 / 3 / 4 / 6 / 7 / 8 / 9（没有写「无」）
- 发现的过期信息：<大脑或文档里与代码不一致的地方；没有写「无」>
```

没有增量块视为报告不完整。Steward 在 G2.5 合并；Dev 不直接大改大脑（只提交增量）。

## 5. 检查点

| 检查点 | 谁 | 做什么 |
|---|---|---|
| G1 确认后 | Doc + Steward | 影响预判：本次会碰哪些模块/不变量/契约；大脑是否需要先更新 |
| G2 完成 | Dev | 写「上下文增量」；列出实际读过的文件 |
| G2.5 | Steward | 合并增量到大脑；更新「最近变更」；标记过期内容 |
| G3 评审 | Review | 读大脑 + 增量 + diff；按测试地图跑回归；写 review-index |
| G3.5（可选） | Steward | 跨模块/跨 CR 的一致性检查；发现隐性耦合 |
| G4 | Steward/Meta | 风险触发的全链路总审；复核大脑与实现是否一致 |

## 6. 会话复用

- **同一 CR 内**：Dev 用同一个会话完成实现与返工；Steward 用同一个会话完成 G1/G2.5/G3.5。
- **Review**：每个 CR 新建会话以保持独立性；同一 CR 的返工可复用会话以保持基线。
- **跨 CR**：一律新建会话，只带大脑 + 相关报告路径，不带上一轮全文。
- 上下文接近上限时：先写增量与交接块，再新开会话；不要带着半截上下文硬撑。

## 7. 大脑维护规则

- 只写稳定事实与导航；不复制代码，不写频繁变化的实现细节。
- 每条关键结论尽量带 `文件:行号`、命令或报告链接。
- 验证命令带「最后验证」日期；超过 90 天标「可能过期」。
- 架构、契约、不变量变化时，Steward 必须在「最近变更」留记录。
- 大脑超过 ~200 行时，把模块细节拆到 `brain/modules/`。
- 大脑与代码冲突时，**以代码 + 实际运行结果为准**，并立即标记大脑过期。

## 8. review-index（评审记忆）

`<文档根目录>/reports/review-index.md` 按模块记录：

| 模块 | 历史缺陷类型 | 高发位置 | 建议检查 |
|---|---|---|---|
| ... | 并发/边界/契约/权限… | 文件:行 | 下次评审优先看什么 |

Review 开工时读它，但不把它当证据；它只用于决定**先看哪里**。每轮评审后追加一行，不写长篇。

## 9. 反模式

- ❌ 每个 Agent 都从 `00-overview` 读到代码，重复付费。
- ❌ 把大脑写成第二份架构文档，没人维护。
- ❌ 大脑过期后仍被当作事实；没有「最后验证」日期。
- ❌ 报告只写「已完成」，不写增量，Steward 无法合并。
- ❌ Review 通读全仓库找问题，而不是按 diff + 影响面 + 测试地图。
- ❌ 为了省 token 跳过关键调用方/测试的阅读。

## 10. 度量

每个 CR 在 `STATUS.md` 或报告里记录：

- 各角色实际读过的文件数 / 是否超出预算
- 重复读同一文件的次数
- G3 发现的 P0/P1 数、Review 漏检数
- 从 G1 到 G3 的耗时与 token（有数据时）

没有度量就无法判断「更高效」是否成立。

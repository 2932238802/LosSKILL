# Skill 写作规范

这份规范只为一件事服务：**让别的 AI 在不读任何说明的情况下，正确加载并正确使用这个 Skill。**

## 1. 目录与命名

```
skills/<skill-name>/
├─ SKILL.md          # 必需
└─ references/       # 可选，按需加载
   └─ xxx.md
```

- 目录名 = frontmatter 的 `name`，全小写 kebab-case，动词或领域开头
- 不要在目录里放脚本、二进制、图片之外的构建产物；Skill 应当是「纯文本可读」
- 一个 Skill 只解决一类任务。任务跨域 → 拆成两个 Skill，在 `SKILLS.md` 里写组合链路

## 2. frontmatter

```yaml
---
name: sandra-sales-qualify        # 必填，与目录名一致
description: |                    # 必填，AI 靠它决定加不加载
  当用户……时使用。输出……。不用于……。
metadata:                         # 选填，给自己溯源用
  source-type: book
  source-title: 桑德拉销售原则（中国本土案例版）
  tags: sales, qualification
---
```

`description` 是唯一会影响「会不会被触发」的字段，必须包含三段：

| 段 | 写法 | 反例 |
|---|---|---|
| 何时用 | 用户会说的**原话**、具体场景 | ❌「涉及销售机会评估时」 |
| 产出什么 | 具体交付物 | ❌「给出建议」 |
| 不用于什么 | 相邻场景 + 该去哪个 Skill | ❌ 省略 |

长度控制在 2–4 句；超过 5 句 AI 反而抓不住重点。

## 3. 正文结构

推荐顺序（不是死规定，但缺项会让 AI 猜）：

1. **触发与不触发** — 与 description 呼应，写得更具体
2. **输入检查** — 缺什么先问，避免凭空编造
3. **核心原则** — 3–7 条，常驻上下文，不依赖附件
4. **执行步骤** — 编号步骤，每步有明确动作与判断点
5. **输出模板** — 可直接套用的骨架（表格/清单/话术）
6. **常见错误** — ❌ / ✅ 对照，最容易被 AI 忽略的行为
7. **边界与判停** — 什么时候必须停、必须转人工
8. **参考资料** — 只写「文件 → 何时读」，不要在这里复制内容

## 4. 渐进披露

- `SKILL.md` 控制在 **500 行以内**；超出就拆到 `references/`
- `references/` 里的文件必须能被单独读懂：开头一句说明「这份文件解决什么问题」
- 正文引用附件用**相对路径**（`references/xxx.md`），不要用绝对路径、不要跨 Skill 引用
- 明确写「每次只读 1 个附件；跨域最多 2 个」，防止 AI 一次性吞掉全部内容

## 5. 蒸馏类 Skill 的额外要求

如果来源是书/视频/课程，保留可溯源性：

- 关键结论标注来源位置（原则编号、章节、时间戳、行号）
- 区分「原文」「我的理解」「案例」，不要把推断写成原文
- 书中无出处的数字，标注「无出处，仅作方向」
- 保留原文的内部张力/矛盾，不要为了自洽而抹平

## 6. 自检清单（提交前逐条过）

- [ ] 目录名 = `name`，kebab-case
- [ ] `description` 含「何时用 / 产出 / 不用于」三段
- [ ] 正文没有任何绝对路径、没有依赖仓库外文件
- [ ] 附件都在 `references/` 内，且只通过相对路径引用
- [ ] 有「不适用」与「判停」两节
- [ ] 输出模板可直接套用，不是抽象描述
- [ ] `SKILLS.md` 已加索引行
- [ ] 在一台干净环境里复制该文件夹后，仍能独立工作

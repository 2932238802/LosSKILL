# 迦智（Jiazhi）工作习惯

> 公司专属；不要复用到其他公司。

- **系统**：DingTalk 文档（`alidocs.dingtalk.com`）、Teambition 任务、GitLab `server01.jz`、CI `build-verify`。
- **任务记录**：参考任务 `6adf0e8fc54cf79de8ebdcfb`。
  - 需求描述：一段话 + 3 条左右工作项，工时写在条目里，同类任务合计 ≤2.5。
  - 交付事项 / 验收事项：各一句话。
  - 备注：只放进度、阻塞、上机状态。
- **MCP**：Teambition 官方 HTTP MCP（OAuth）读写任务；`dingtalk-doc` Cookie 只读；`dws` 组织 CLI 权限未开通。
- **项目口径**：车端参数统一用 `flash-agv-parameters`；App 遥控 WS 协议 V1.0；设计文档与协议冲突时以协议为准。
- **Git/CI**：`flash-agv` 分支/ tag；一单一个 commit；tag `1.2611.1+remote-control`。旧基线 `1f808aaa` 的 branch `#163776`、tag `#163777` 均 Passed；2026-11-23 嫁接后分支 `feat/remote-control-web` @ `da2ae3e1` 已推送，tag 是否跟随待定。
- **公司边界**：任务 ID、链接、字段 ID、凭证、MCP 配置只在本目录使用。
- **文档归档**：Doc Agent 开发文档 → `docs/archive/<YYYYMMDD>/N-<主题>-开发文档.md`，同日放 `README.md` 子索引（状态总览 + 待决事项）；角色执行报告 → `docs/reports/`；两者都登记 `WORKLOG.md`。
- **配置改动留痕**：修改 `flash-agv/config/*.json` 时，必须在 Teambition 单备注：①改了哪个 JSON、为什么；②日后需同步到车型参数（`flash-agv-parameters` proto）；③对应 JSON 变更的 commit 哈希（未提交时先记「待提交后补哈希」）。项目组后续统一迁移 JSON→车型参数时，以该哈希对应的 JSON 为准。
- **单子备注格式**：进度写进任务「备注」字段（`note`），不是评论；**一条 = 一个时间 + 一件事，只追加不覆盖**（各时间块各自保留，不合并/不改写）；只写产出与结果，不写过程、不写「待确认/阻塞/剩余」；结果用**人话**说明哪些测试通过、覆盖什么，不堆裸数字；时间到分钟，短句分行；提交后补录哈希。
- **临时目录**：脚本、构建目录、测试临时文件统一放 `D:\Temp`（WSL `/mnt/d/Temp`），不放 `/tmp`、CWD 或仓库目录，也不写 C 盘默认临时目录；测试代码尊重 `TMPDIR`/`*_TEST_TMPDIR`，本地运行时设 `TMPDIR=/mnt/d/Temp`。
- **人工文档审阅清单**：`JZ/docs/人工文档审阅清单.md` 只列**必要审阅**（需求/G1/开发文档/材料/自测交付/关键评审结论）；持续变动或过程性文件（STATUS、WORKLOG、README 索引、清单本身、脚本、存档 patch、逐次返工报告）不列入；「完成」= 审阅发生在文件最后修改之后，文件再改则运行 `docs/scripts/doc_review_sync.py` 自动取消勾选。
- **工时评估标准**：单位人天，1 人天=10 绩效积分；固定 7 档 `0.2/0.5/1/1.5/2/2.5/3`；单任务≤3，超 3 拆分；任务类型分方案设计/开发实现/系统联调，复杂需求先拆分再评估；工时写在需求描述条目里，交付/验收事项不重复写。来源：钉钉《开发任务参与度评估标准》《任务分档参与度速览表》（2026.3.27 有效工时优化会议），之后所有单子按此执行。
- **任务单字段简洁**：需求描述 1–2 句说明为什么做/做什么 + 短句工作项（各带 7 档工时之一）；交付事项一句话列交付物，不复述需求、不写过程；验收事项写判定口径 + 报告链接 + 版本号（=tag）。
- **开发文档先于开发**：Doc Agent 必须先产出 `docs/archive/<YYYYMMDD>/N-<主题>-开发文档.md`，再派 Dev Agent；派单简报必须带【开发文档】绝对路径并写明「以文档为准，偏离在报告说明」。Dev 报告要加「对应开发文档」与「上下文增量」两节；Dev 完成后由 Doc 回填文档验证结果、STATUS 与当日 README 索引，「待回填」不留过夜。看着机械的活（rebase/重放/升级依赖）同样含决策，同样要先写。
- **材料与交付两目录**：`docs/materials/`（输入侧：任务单/协议/规格书/设计文档的转写摘录 + `材料清单与差距表.md` 记来源、可用状态、代码基线、已冻结决策）与 `docs/deliverables/`（输出侧：`钉钉-<主题>自测报告-<日期>.md` 源文件 + `钉钉链接.md` 知识库链接索引）。每单固定两份：有新外部材料就落 materials 并登记，验收要自测报告就落 deliverables 并发布钉钉、删除个人副本；两者都进人工审阅清单。区分：`reports/` 是角色间过程记录，`materials/` 是外部输入，`deliverables/` 是给人看的交付件。
- **分支清理**：迁移/重放/任务完成或 tag 落定后，删除备份分支（`backup/*`）、临时探针分支（`tmp/*`、`graft/*`）与多余可删的远端分支，不让远端分支变乱；删前先确认新 tip 已推送、tag 已跟随、CI 有结果（或该轮明确放弃），**只删我们自己创建的分支；别人创建的分支一律不删、不改**（不 force push、不 rebase 他人分支）；收尾汇报列「已删/保留」清单。
- **LosSKILL 必须提交**：每次修改 `LosSKILL`（尤其 `work/jiazhi/habits.md`）后必须立即 `git add` + 英文 commit 信息 + `git push`，不留在本地未提交状态。
- **tag 命名**：tag 一律 `<版本>-N`（如 `1.2611.1+remote-control-1`），每次打 tag 名字必须不同，**禁止复用/移动已有 tag**；移动或删除旧 tag 属 A3 需用户明确同意，事后同步单子「验收事项」与交付文档里的版本号。
- **测试归 Doc、其余归 Dev**：测试环节（本机/目标机/上机联调、日志与数据采集、按 AC 判读、回填自测报告与 STATUS、同步 Teambition 备注）由 Doc Agent 直接执行；功能实现/返工/代码与构建改动派 Dev Agent。Review/Meta 职责不变。
- **架构事实先查文档站（仅 flash-agv 项目）**：**仅当前项目适用，换项目先找该项目的文档入口，不得默认套用本站结构**；仓库自带文档站 `http://172.18.118.243:8080/`（`?doc=` 与站点相对路径同源，原文路径即直链）。分工：`功能设计/` 写行为规则（正文即最终口径）、`开发手册/` 写命名空间与模块边界、`操作手册/` 写怎么跑、`测试与验收/` 写可机检用例，实现方案 Spec 在仓库外。新需求先按 `功能设计/` 固定结构写行为规则（概览=参与模块/范围/非目标/关键约束；功能点=触发条件→行为→输出；首行状态，「待评审」不构成实施授权），提交前跑 `node scripts/docs/check_mermaid.mjs`；用例另写 `测试与验收/TC-xxx.md`，判定写字段名与取值。我们的 `LosAngelousDocs` 只放交付侧文档，行为规则与用例不复制第二份。命名空间用 `python tools/check_module_namespace.py` 判，不用 grep。
